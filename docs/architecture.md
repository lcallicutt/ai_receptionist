# Architecture Overview

## Product structure

Two portals plus a public marketing site, all in one Next.js App Router app:

| Area | Route prefix | Access |
| --- | --- | --- |
| Public site | `/`, `/features`, `/industries`, `/pricing`, `/demo`, `/contact`, `/book-a-demo`, `/privacy`, `/terms`, `/login` | Public |
| Client Business Portal | `/app/*` | Organization members (owner / manager / member / read_only) |
| FlowNet Admin Portal | `/admin/*` | Platform admins (`users.is_platform_admin`) |

## Multi-tenancy

- Every tenant-owned table carries `organization_id` with a foreign key.
- **Server-side authorization is the only authority.** `src/lib/auth/guards.ts`
  resolves the authenticated user's membership before any org data is touched:
  - `requireUser()` — session → user row
  - `requireOrgContext(orgId?)` — verifies membership; never trusts an org ID
    from the browser without checking `organization_members`
  - `requireOrgRole(role)` — rank-based role checks
  - `requirePlatformAdmin()` — FlowNet admin portal gate
- `src/middleware.ts` is only a fast cookie-presence redirect at the edge;
  real checks happen in layouts, pages, and server actions.

## Authentication

Self-contained credentials auth (no external dependency required to run):

- Passwords: scrypt (Node crypto), constant-time verify — `src/lib/auth/passwords.ts`
- Sessions: HS256 JWT in an httpOnly, SameSite=Lax cookie — `src/lib/auth/session.ts`
- `AUTH_SECRET` is required in production; a dev-only fallback secret is used
  otherwise (and rejected in production builds).

The auth surface is small and isolated in `src/lib/auth/` so Clerk (or another
provider) can replace it without touching feature code.

## Database layer

- Drizzle ORM, schema in `src/lib/db/schema.ts`, migrations generated by
  drizzle-kit into `drizzle/`.
- `getDb()` (`src/lib/db/index.ts`) returns a lazily-initialized singleton:
  - `DATABASE_URL` set → postgres-js against Neon/Postgres
  - unset → embedded PGlite database in `.data/` (dev/demo/tests), auto-migrated
- Plan limits and feature access live in `src/lib/plans.ts` and are seeded into
  `plans` / `plan_features`. Enforcement helpers (`planAllows`, `planLimit`,
  `planLimitReached`) are used server-side; UI restrictions are cosmetic only.

## Provider adapters (later phases)

Core business services never talk to vendors directly. Each integration goes
through an interface with swappable implementations (see
[provider-adapters.md](provider-adapters.md)): `VoiceProvider`,
`TelephonyProvider`, `SMSProvider`, `CalendarProvider`, `CRMProvider`,
`EmailProvider`, `AutomationWebhookProvider`.

## Directory map

```
src/
  app/
    (marketing)/       public pages (shared header/footer layout)
    login/             credentials login
    app/               client portal (auth-guarded layout)
    admin/             FlowNet admin portal (platform-admin-guarded layout)
    api/health/        liveness + DB check
  components/
    ui/                design-system primitives (button, card, badge, input…)
    marketing/         public-site components
    portal/            portal shells and navigation
  lib/
    auth/              passwords, sessions, guards, server actions
    db/                schema, client, migrate, seed
    plans.ts           plan definitions + server-side enforcement
    demo-scenarios.ts  scripted public demo content (labeled simulated)
  middleware.ts        edge cookie gate for /app and /admin
tests/                 vitest suites (incl. tenant isolation on real Postgres)
drizzle/               generated SQL migrations
```
